# Backend API

Запуск из корня проекта:

```powershell
docker compose up -d --build backend
```

Compose запускает PostgreSQL и MinIO как зависимости backend. API доступен на
`http://localhost:3001/api`. Изменения Go требуют пересборки образа.

## Доступ к операциям записи

GET/HEAD-запросы чтения публичны. Все остальные методы API, кроме OPTIONS,
требуют заголовок `Authorization: Bearer <ADMIN_API_TOKEN>`. Это административный
токен, общий для доверенных инструментов записи; пользовательских аккаунтов пока нет.

В Postman откройте **Authorization → Bearer Token** и вставьте токен. Можно задать
его на уровне коллекции, а у запросов выбрать **Inherit auth from parent**.
Без токена или с неверным токеном операции записи возвращают `401` до вызова БД/MinIO.
Если `ADMIN_API_TOKEN` не настроен на сервере, запись отключена и возвращает `503`.

Для Docker задайте `ADMIN_API_TOKEN` в `.env` в корне репозитория (рядом с Compose),
затем выполните `docker compose up -d --build backend`. При запуске Go напрямую
передайте переменную окружения процессу backend. Токен должен содержать минимум
32 байта без пробелов; используйте криптографически случайный секрет.

Не добавляйте токен в `VITE_*`, HTML, ссылки или исходники фронтенда. Файлы `.env`
игнорируются Git. Внешний API должен работать через HTTPS, чтобы заголовок с токеном
не передавался открытым текстом. Для смены токена измените переменную и перезапустите
backend; предыдущий токен перестанет работать.

## Редактирование из админки

Все маршруты ниже требуют `Authorization: Bearer <ADMIN_API_TOKEN>`:

| Метод и маршрут | Действие |
| --- | --- |
| `POST /api/admin/verify` | Проверка токена, ответ `204` |
| `POST /api/characters` | Создание героя |
| `PUT /api/characters/{uuid}` | Изменение имени, описания и роли |
| `POST /api/skills` | Создание скилла с `character_uuid` |
| `PUT /api/skills/{uuid}` | Изменение скилла, включая его героя |
| `POST /api/media-metadata` | Загрузка нового медиа |
| `PUT /api/media-metadata/{id}` | Замена файла существующего медиа |
| `DELETE /api/media-metadata/{id}` | Удаление медиа, ответ `204` |

PUT героев/скиллов использует ту же JSON-структуру, что POST, и возвращает `200`.
UUID и числовой ID записи сохраняются. При переносе скилла собственное медиа
остаётся связано с его UUID. PUT медиа принимает те же multipart-поля, что POST;
владелец и media_type должны совпадать с существующей записью.

У скилла есть `sort_order` (целое число от 0 до 2147483647). POST без этого поля
использует 0, PUT без поля сохраняет прежнее значение. Категория задаётся `type`.
Внутри категории frontend сортирует по `sort_order`, затем по `id` для стабильного
порядка при одинаковых значениях. Существующие записи после миграции получают 0.

Для существующей БД один раз примените `migrations/000002_skill_order.up.sql`
перед запуском нового backend. В Compose файл также подключён для инициализации
новой БД; init-скрипты не применяются повторно к уже созданному volume.

Замена сначала загружает новый объект, затем атомарно меняет object_key в БД и
удаляет старый объект. При ошибке записи удаляется только новый объект. DELETE
сначала удаляет метаданные, затем файл. Если MinIO не может выполнить очистку,
ошибка пишется в лог: недоступный для очистки объект может остаться в бакете,
но API больше на него не ссылается. Смена object_key обновляет версию ссылки во
фронтенде, чтобы после замены браузер показывал новый файл.

## Загрузка медиа

`POST /api/media-metadata` принимает **multipart/form-data**. В Postman выберите
Body → form-data и добавьте поля:

| Поле | Тип в Postman | Значение |
| --- | --- | --- |
| `owner_type` | Text | `CHARACTER`, `SKILL` или `EMOTE` |
| `owner_uuid` | Text | UUID существующей сущности из ответа API |
| `media_type` | Text | `ICON`, `RENDER` или `DEMO` |
| `file` | File | Файл с компьютера |

Не задавайте Content-Type вручную: Postman добавляет multipart boundary сам.
Для `ICON` и `RENDER` поддерживаются PNG, JPEG, GIF и WebP; для `DEMO` — MP4
и WebM. Максимальный размер одного файла — 32 MiB. Тип проверяется по содержимому.

Успешная загрузка возвращает `201` и метаданные с `id`, `owner_type`, `owner_uuid`,
`media_type`, `object_key`. Сам файл хранится в приватном бакете MinIO, а метаданные
— в PostgreSQL. Ключ имеет вид `character/{uuid}/icon/{random-uuid}`.

- `GET /api/media-metadata?owner_type=CHARACTER&owner_uuid={uuid}` — метаданные владельца.
- `GET /api/media-metadata/{id}/file` — содержимое файла через backend.
- `GET /api/characters` и `GET /api/characters/{uuid}` — персонажи с массивом `media_metadata`.
- `GET /api/skills`, `GET /api/skills/{uuid}` и `GET /api/characters/{uuid}/skills` — скиллы с их собственными медиа.

Для одного владельца разрешён один файл каждого media_type. Повторная загрузка
того же типа возвращает `409`, прежний файл сохраняется. При ошибке записи в БД
новый файл удаляется из MinIO; ошибки очистки записываются в логи backend.
Неизвестный владелец возвращает `404`; некорректные поля — `400`, неподдерживаемый
формат — `415`, превышение размера — `413`, недоступный MinIO — `502`.

Связь с владельцем определяется парой `(owner_type, owner_uuid)`, а не его числовым
ID. Для новой сущности добавьте значение в PostgreSQL enum `owner_type`, таблицу
с колонкой `uuid` и зарегистрируйте её через `mediaRepository.RegisterOwnerType`
при настройке приложения. `SKIN` пока не зарегистрирован: таблицы skins ещё нет.
Новая таблица не требует добавления колонок в `media_metadata`.

## Подключение PostgreSQL

`DATABASE_URL`, если задан, имеет приоритет и должен быть корректным URL.
Специальные символы пароля в нём требуют percent-encoding (например, `#` → `%23`,
`%` → `%25`, `/` → `%2F`, `@` → `%40`). Не кодируйте весь URL целиком.

Альтернатива — убрать `DATABASE_URL` и передать `POSTGRES_USER`,
`POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DBNAME` отдельно.
В этом случае backend сам экранирует пароль. В Docker используйте host `postgres`;
в Compose замените строку `DATABASE_URL` на эти пять переменных.

## MinIO

Backend читает `MINIO_ENDPOINT` (без схемы URL), `MINIO_ACCESS_KEY`,
`MINIO_SECRET_KEY`, `MINIO_BUCKET`, `MINIO_SECURE`. Локальные значения по умолчанию:
`localhost:9005`, `admin`, `12345678`, `squadragram-media`, `false`.
В Docker endpoint настроен как `minio:9005`. Бакет создаётся при первой загрузке.

## Проверки

```powershell
cd squadragram-backend
go test ./...
```

Дополнительные интеграционные проверки:

```powershell
$env:TEST_DATABASE_URL = 'postgres://postgres:postgres@127.0.0.1:5432/postgres?sslmode=disable'
$env:TEST_MINIO_ENDPOINT = 'localhost:9005'
go test ./cmd ./internal/repository/media_metadata ./pkg/minio -v -count=1
```

Сквозной тест в cmd проходит сценарий админки через реальные маршруты: создание и
редактирование героя/скилла, загрузка, замена, чтение и удаление медиа. Он использует
изолированную схему PostgreSQL и удаляет временные объекты MinIO.

Тест PostgreSQL создаёт изолированную схему, применяет начальную миграцию и
откатывает всё транзакцией. Тест MinIO удаляет свой временный объект после проверки.
Без переменных TEST_* эти интеграционные проверки пропускаются.
